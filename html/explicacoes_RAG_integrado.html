Bloco 1 · Ingestion

Entendendo o 1_ingestion.py

Do arquivo bruto ao chunk rastreável — uma linha de montagem em 4 etapas.

1 A estrutura de dados: Chunk

Este arquivo é o primeiro bloco de um pipeline RAG. Antes de um modelo conseguir "consultar" seus documentos, alguém precisa transformar PDFs/TXTs em pedaços pequenos de texto (os chunks) que possam ser vetorizados e buscados depois.

Pense nele como uma linha de montagem em 4 etapas:

[Arquivos brutos] → [Limpeza] → [Chunking] → [Lista de Chunks]
@dataclass
class Chunk:
    id: str          # ex: "manual.pdf_12"
    text: str        # o texto em si
    source: str      # caminho do arquivo original
    page: int        # número da página
    chunk_idx: int   # índice sequencial do chunk
    doc_hash: str    # SHA-256 do arquivo (governança)
Por que isso importa? Um chunk não é só texto — ele precisa saber de onde veio (rastreabilidade). Sem isso, não dá para citar fontes na resposta final. O doc_hash é um bônus de governança: se o PDF mudar, o hash muda, e você sabe que aquele chunk está obsoleto.

2 Limpeza de texto: clean_text()

PDFs são notoriamente sujos. Colunas viram texto embaralhado, hífens quebram palavras, e sobram caracteres invisíveis. A função aplica 5 tratamentos em sequência:

EtapaO que fazExemplo
1. Normalização Unicode (NFKC)Unifica caracteres "parecidos"ﬁ (ligadura) → fi
2. Remove soft-hyphensTira hífens invisíveisinfor­mação → informação
3. Junta palavras quebradasinfor-\nmação → informaçãoregex (\w)-\s*\n\s*(\w)
4. Colapsa espaços"a b c" → "a b c"—
5. Normaliza quebras de linha\n\n\n\n → \n\nevita "buracos"

A ordem importa. Se você colapsasse espaços antes de juntar palavras com hífen, a regex -\s*\n\s* deixaria de funcionar porque o \n já teria virado espaço.

3 Leitores de documentos

Três funções com a mesma assinatura (Path → list[tuple[str, int]]), o que permite tratá-las de forma intercambiável:

  • load_pdf: itera página por página, retornando (texto_limpo, num_página). Páginas em branco são descartadas.
  • load_text: para .txt e .md, lê tudo como uma única "página 1".
  • load_document: é um roteador via dicionário:
loaders = {".pdf": load_pdf, ".txt": load_text, ".md": load_text}
return loaders[suffix](path)

Esse padrão (dicionário de funções) é mais limpo que um if/elif gigante e fácil de estender: adicionar .docx é só uma linha.

compute_hash() complementa: lê o arquivo em blocos de 8 KB e calcula o SHA-256. Ler em streaming evita carregar um PDF de 500 MB inteiro na memória.

4 O coração: split_into_chunks()

Aqui é onde a janela deslizante acontece. A ideia é dividir o texto em pedaços de tamanho fixo, mas com uma sobreposição entre eles:

chunk_size = 500 chunk_overlap = 100 step = 400 (= 500 - 100) [------ chunk 0 ------] [------ chunk 1 ------] [------ chunk 2 ------]

Por que sobrepor? Porque a fronteira entre dois chunks pode cortar uma frase no meio. Com sobreposição, a ideia que ficou "pela metade" no chunk anterior aparece inteira no próximo. É uma rede de segurança contra perda de contexto.

start = 0
while start < len(text):
    end = start + cfg.chunk_size
    chunk_text = text[start:end].strip()
    if len(chunk_text) >= cfg.min_chunk_size:  # descarta migalhas
        chunks.append(Chunk(...))
    start += step   # avança MENOS que chunk_size → sobreposição
  • min_chunk_size filtra "sobras" do fim do texto — chunks de 30 caracteres são ruído para o retriever.
  • doc_chunk_offset permite que o chunk_idx continue numerando entre páginas do mesmo documento.

5 Orquestrador: ingest_directory()

Para cada arquivo suportado na pasta: calcula o hash → carrega páginas → chunking → carimba o hash → acumula tudo em all_chunks.

Pontos de robustez:

  • try/except por arquivo → um PDF corrompido não derruba o pipeline inteiro.
  • Se o diretório não existe, raise FileNotFoundError (falha explícita).
  • Se não há arquivos, retorna [] com aviso amarelo — não é erro, é aviso.

6 Execução standalone

Permite rodar o arquivo isoladamente:

python 1_ingestion.py

Procura a pasta ../data, processa tudo e imprime uma tabela Rich com os 10 primeiros chunks (ID, fonte, página, tamanho, prévia). É uma forma rápida de inspecionar visualmente a qualidade do chunking antes de seguir para o próximo bloco.

Bloco 2 · Indexing

Entendendo o 2_indexing.py

De chunks de texto a vetores buscáveis por significado — o "cérebro semântico" do pipeline.

Este é o Bloco 2 do pipeline RAG: pega os chunks do Bloco 1 e os transforma em vetores numéricos que o ChromaDB pode buscar por similaridade semântica.

[Chunks de texto] → [Ollama: texto → vetor] → [ChromaDB: vetor + metadata]

O conceito central é o embedding:

Embeddings são representações matemáticas de significado. Textos semanticamente similares ficam "próximos" no espaço vetorial, permitindo busca por relevância, não por palavras-chave.

"cachorro" e "cão" não têm letra em comum na busca tradicional, mas em espaço vetorial ficam vizinhos.

1 O problema dos imports: números em nomes de arquivo

try:
    from ingestion import Chunk
except ModuleNotFoundError:
    import sys
    sys.path.insert(0, str(Path(__file__).parent))
    from importlib import import_module
    _m = import_module("1_ingestion")
    Chunk = _m.Chunk

Por que esse rodeio? Porque 1_ingestion.py começa com número — e import 1_ingestion é erro de sintaxe. Saídas: tentar from ingestion import Chunk; senão, usar import_module("1_ingestion") que aceita strings em runtime.

Lição: Python não "sabe" que 1_ é prefixo de ordenação — é só texto. Quem contorna isso é o código.

2 Cliente ChromaDB: get_chroma_client()

def get_chroma_client(cfg: ChromaConfig = chroma_cfg) -> chromadb.PersistentClient:
    Path(cfg.persist_dir).mkdir(parents=True, exist_ok=True)
    client = chromadb.PersistentClient(
        path=cfg.persist_dir,
        settings=Settings(anonymized_telemetry=False),
    )
    return client
LinhaO que faz
mkdir(parents=True, exist_ok=True)Cria a pasta de persistência; exist_ok=True evita erro se já houver
PersistentClient(path=...)Abre um banco em disco — os vetores continuam lá se o processo morrer
anonymized_telemetry=FalseDesliga telemetria do ChromaDB (privacidade)

Contraste: chromadb.Client() (em memória) perde tudo ao fechar o processo. PersistentClient é a escolha correta para produção.

3 A coleção: get_or_create_collection()

collection = client.get_or_create_collection(
    name=cfg.collection_name,
    metadata={"hnsw:space": cfg.distance_metric},
)

Uma collection no ChromaDB é o equivalente a uma "tabela" em SQL. O detalhe crítico é metadata:

{"hnsw:space": "cosine"}   # ou "l2", ou "ip"
MétricaNomeQuando usar
cosineSimilaridade de cossenoPadrão em RAG — mede ângulo, ignora magnitude
l2Distância euclidianaSensível à magnitude; raramente ideal para texto
ipInner productPara modelos treinados com essa métrica

Aviso: essa metadata só é aplicada na primeira criação da collection. Se você mudar distance_metric depois, o ChromaDB ignora — é preciso apagar a pasta de persistência ou renomear a collection.

4 O coração: index_chunks()

4.1 Guarda de vazio

if not chunks:
    console.print("[yellow]⚠ Nenhum chunk para indexar.[/yellow]")
    return 0

Retornar 0 permite ao chamador usar o retorno numericamente sem checar None. Fail-fast elegante.

4.2 Barra de progresso com Rich

with Progress(
    SpinnerColumn(),
    TextColumn("[progress.description]{task.description}"),
    BarColumn(),
    TaskProgressColumn(),
    console=console,
) as progress:
    task = progress.add_task("Indexando...", total=len(chunks))

Embeddings podem levar minutos com centenas de chunks — sem feedback, o usuário acha que travou.

4.3 Batching — a decisão mais importante

for i in range(0, len(chunks), batch_size):
    batch = chunks[i : i + batch_size]
    batch_texts = [c.text for c in batch]
    batch_embeddings = get_embeddings(batch_texts)

Por que não indexar tudo de uma vez? Com 1.000 chunks: memória estoura, timeout perde tudo, sem feedback. Com batch_size=50:

  • Pico de memória 50× menor.
  • Se o batch 12 falhar, você só perdeu 50 chunks.
  • Barra de progresso anda a cada ~1–2 segundos.
  • Chamadas HTTP ao Ollama têm payloads menores.

4.4 O upsert — coração da indexação

collection.upsert(
    ids=[c.id for c in batch],
    embeddings=batch_embeddings,
    documents=batch_texts,
    metadatas=[...],
)
CampoO que éPapel no RAG
ids"manual.pdf_12"Chave primária. Permite atualizar/deletar sem duplicar
embeddings[0.021, -0.134, ...]O vetor de significado. Base da busca
documentsO texto originalRetornado na busca — o LLM vai ler isso
metadatasDicts com source, page, etc.Permite filtrar a busca

Redundância proposital: o texto aparece duas vezes — como embeddings (busca) e como documents (leitura). O primeiro é matemática; o segundo é o que o LLM vai ler. Ambos são necessários.

4.5 upsert vs add

  • add: falha se o id já existe.
  • upsert: sobrescreve se existe, insere se não.

Essencial em pipelines re-executáveis. Casa com o doc_hash do Bloco 1: se o PDF mudou, o hash muda, e o upsert substitui os chunks antigos.

4.6 Metadata de governança

metadatas=[{
    "source": c.source,
    "page": c.page,
    "chunk_idx": c.chunk_idx,
    "doc_hash": c.doc_hash,
    "status": "vigente",
    "version": "v1.0"
} for c in batch]

Os dois últimos campos são governança de dados:

  • status: "vigente" — permite marcar chunks como obsoletos sem deletar.
  • version: "v1.0" — rastreia qual iteração gerou o chunk.

Isso viabiliza operações como:

# "Só responda com base em documentos vigentes"
collection.query(..., where={"status": "vigente"})

Ponto de atenção: o doc_hash é incompleto. Se o chunking mudou (chunk_size 500 → 300), os chunks antigos não são sobrescritos — o id muda e eles ficam como lixo no banco.

4.7 Contagem final

total = collection.count()
console.print(f"[green]✓ Indexação concluída! Total na coleção: {total}[/green]")
return total

collection.count() retorna o total acumulado. Se você indexou 500 mas count() retornou 700, há chunks órfãos de execuções anteriores.

✦ Resumo em uma frase

Este módulo transforma a lista de Chunks do Bloco 1 em uma coleção ChromaDB persistente, onde cada chunk vira {id, vetor, texto, metadata}, permitindo ao Bloco 3 responder perguntas como "quais trechos são semanticamente mais próximos da pergunta do usuário?".

⚠ Possíveis melhorias

  1. Idempotência da métrica de distância — hnsw:space só é lido na criação. Vale um try/except verificando se a collection existente tem a métrica esperada.
  2. Chunks órfãos — quando chunk_size muda, os antigos ficam no banco. Um mecanismo de "limpeza por doc_hash obsoleto" manteria o índice enxuto.
  3. Falha no meio do batch — sem retry, um erro no batch 5 deixa os batches 0-4 gravados mas o trabalho incompleto.
  4. status/version hardcoded — deveria vir do config.py.

Bloco 3 · Retrieval

Entendendo o 3_retrieval.py

A pergunta encontra os documentos — busca vetorial, filtros e re-ranking.

Este é o Bloco 3 do pipeline RAG: o momento em que a pergunta do usuário finalmente "encontra" os documentos. Pense nele como o caixa de uma biblioteca:

[Pergunta em texto] → [Vira vetor] → [Busca os vizinhos mais próximos] → [Top-K chunks] ↓ (opcional) Re-ranking
A busca vetorial encontra documentos por SIGNIFICADO, não por palavras-chave.

Se o usuário pergunta "Quais são os direitos dos funcionários?", o sistema não procura a palavra "direitos" literalmente — procura chunks cujo vetor está próximo. Um chunk que diga "os colaboradores têm garantidos os seguintes benefícios…" pode ser retornado mesmo sem palavras em comum.

1 O tipo RetrievedChunk

@dataclass
class RetrievedChunk:
    id: str
    text: str
    source: str
    page: int
    distance: float
    score: float
CampoChunk (B1)RetrievedChunk (B3)
id, text, source, page✅✅
chunk_idx, doc_hash✅❌
distance❌✅
score❌✅

Por que dois tipos? O Chunk é o dado em repouso (pré-indexação); o RetrievedChunk é o dado em movimento (resultado de uma consulta), carregando informação que só existe após a busca.

Distinção: distance e score são duas faces da moeda. O ChromaDB devolve distância (menor = melhor); o score é o inverso convertido para "similaridade" (maior = melhor).

2 search() — o coração

2.1 Vetorizar a pergunta

query_embedding = get_single_embedding(query)

Simetria fundamental do RAG: a pergunta e os documentos precisam ser vetorizados pelo mesmo modelo.

2.2 A consulta ao ChromaDB

k_initial = cfg.top_k * 5 if cfg.rerank else cfg.top_k
n_results = min(k_initial, collection.count())

if n_results == 0:
    return []

results = collection.query(
    query_embeddings=[query_embedding],
    n_results=n_results,
    where=where,
    include=["documents", "metadatas", "distances"],
)

(a) Buscar mais quando for re-rankear

Re-ranking só compensa com margem. Se o usuário quer top_k=5:

  • Sem rerank: peça 5.
  • Com rerank: peça 25 ao Chroma → Cross-Encoder refina → 5 melhores.
EstágioObjetivoSacrifícioVelocidade
1. Vector searchRecall altoPrecisão menorMilissegundos
2. Cross-EncoderPrecisão altaCusto computacionalCentenas de ms

(b) Nunca pedir mais do que existe

n_results = min(k_initial, collection.count())

Se a coleção tem 12 chunks e você pede 25, o ChromaDB lança erro. O min() evita o problema.

(c) O filtro where — busca híbrida

search("direitos", collection, where={"status": "vigente"})
search("férias", collection, where={"page": {"$gte": 10}})

Isso transforma a busca vetorial pura em busca híbrida: "os chunks mais similares, MAS apenas entre os vigentes e na página ≥ 10".

No Bloco 2 vimos status: "vigente" sendo carimbado; aqui ele é usado. Sem o where, chunks obsoletos voltariam e o LLM responderia com base em versões desatualizadas.

O include exclui embeddings do retorno — desnecessário e caro trafegar 768 floats por chunk.

2.3 Parsear em RetrievedChunk

for chunk_id, doc, meta, dist in zip(
    results["ids"][0],
    results["documents"][0],
    results["metadatas"][0],
    results["distances"][0],
):
    chunks.append(
        RetrievedChunk(
            id=chunk_id,
            text=doc,
            source=meta.get("source", "desconhecido"),
            page=int(meta.get("page", 0)),
            distance=dist,
            score=1.0 - dist,          # ← conversão fundamental
        )
    )

O [0] depois de cada chave

results["ids"] retorna lista de listas — uma por query. Como passamos uma única query, só a posição [0] interessa.

A conversão score = 1.0 - dist

A fórmula mais importante da função. Com métrica cosine, a distância varia de 0 (idêntico) a 2 (opostos). Similaridade = complemento:

similaridade = 1 - distância • distance = 0.0 → score = 1.0 (perfeito) • distance = 0.5 → score = 0.5 (razoável) • distance = 1.0 → score = 0.0 (ortogonal)

Se você mudasse a métrica para l2, essa conversão deixaria de fazer sentido — l2 não tem esse limite superior. O código assume cosseno silenciosamente.

meta.get("source", "desconhecido") e int(meta.get("page", 0)) são defesas: metadata é JSON, então page pode voltar como string; o int() normaliza.

2.4 Re-ranking opcional

if cfg.rerank and chunks:
    console.print("[dim]🔄 Aplicando Re-ranking (Cross-Encoder)...[/dim]")
    encoder = CrossEncoder(cfg.rerank_model)
    pairs = [(query, c.text) for c in chunks]
    scores = encoder.predict(pairs)

    for chunk, score in zip(chunks, scores):
        chunk.score = float(score)

    chunks = sorted(chunks, key=lambda x: x.score, reverse=True)

return chunks[:cfg.top_k]

Cross-Encoder vs Bi-Encoder

AspectoBi-EncoderCross-Encoder
Como codificaQuery e doc separadamenteQuery + doc juntos
Pré-computar?✅ Sim❌ Não
Velocidade⚡ Milissegundos para milhões🐢 Centenas de ms para dezenas
QualidadeBoaExcelente
Uso1º estágio (recall)2º estágio (precisão)

Bi-encoder é como perguntar a duas pessoas separadamente "descreva essa pergunta" e "descreva esse texto" e comparar. Cross-encoder é como colocar as duas na mesma sala e perguntar "esse texto responde a essa pergunta?".

Por isso: bi-encoder filtra muitos → cross-encoder refina poucos.

O if cfg.rerank and chunks:

Duas guardas: respeita a configuração, e evita carregar o modelo (segundos, centenas de MB) para lista vazia.

Os scores mudaram de escala

  • Sem rerank: chunk.score ∈ [0, 1] (cosseno).
  • Com rerank: chunk.score ∈ (-∞, +∞) (logits).

Bom para ranquear, ruim para exibir como "confiança". Se for expor num dashboard, normalize com sigmoid.

chunks[:cfg.top_k]

O truncamento final. Funciona em ambos os casos porque o ChromaDB já devolve ordenado por distância crescente (= score decrescente). É uma invariante do ChromaDB.

3 format_context() — empacotando para o LLM

def format_context(chunks: list[RetrievedChunk], max_chars: int = 3000) -> str:
    context_parts: list[str] = []
    total_chars = 0

    for i, chunk in enumerate(chunks, start=1):
        source_name = Path(chunk.source).name
        header = f"[Trecho {i} | Fonte: {source_name} | Pág. {chunk.page}]"
        block = f"{header}\n{chunk.text}"

        if total_chars + len(block) > max_chars:
            break

        context_parts.append(block)
        total_chars += len(block)

    return "\n\n---\n\n".join(context_parts)

Resolve um problema que só aparece no Bloco 4: o LLM tem janela de contexto limitada. 25 chunks de 500 caracteres = 12.500 — pode não caber ou diluir a pergunta em ruído.

O cabeçalho estruturado

header = f"[Trecho {i} | Fonte: {source_name} | Pág. {chunk.page}]"

Rastreabilidade embutida. Dois propósitos: (1) o LLM aprende a citar fontes; (2) o humano vê exatamente de onde veio cada trecho para debug.

O break — corte por tamanho

Para na primeira vez que estoura. Conservador e previsível — perde a chance de incluir chunks pequenos que viriam depois, mas o output é estável. Em RAG, previsibilidade > otimização.

max_chars=3000 ≈ 750 tokens — seguro até para modelos pequenos.

Invariantes implícitas:

  1. Métrica do Chroma é cosine (senão 1 - dist está errado).
  2. Chunks do Bloco 2 foram vetorizados com o mesmo modelo.
  3. O CrossEncoder funciona em português.

⚠ Possíveis melhorias

  1. CrossEncoder recriado a cada chamada — em servidor web, cada request carrega o modelo (segundos, centenas de MB). Usar @lru_cache ou lazy loading.
  2. Sem normalização pós-rerank — score muda de semântica conforme rerank está ligado. Normalizar com sigmoid ou documentar.
  3. where não é validado — filtro malformado explode sem contexto.
  4. Sem tratamento para falha do Ollama — erros técnicos indistinguíveis para o usuário.
  5. format_context não usa continue — um chunk grande no meio descarta todos os seguintes.
  6. Sem timing — não há medição de quanto tempo cada etapa leva.

Bloco 4 · Generation

Entendendo o 4_generation.py

A pergunta e o contexto viram prompt — e o LLM finalmente responde.

Este é o Bloco 4 — o último — do pipeline RAG: o momento em que o LLM finalmente responde ao usuário. Pense nele como o redator final:

[Pergunta] + [Contexto recuperado] → [Prompt estruturado] → [Ollama] → [Resposta]

É o bloco mais curto em linhas de código e o mais crítico em qualidade final. Erros nos blocos 1–3 degradam; erros aqui aparecem na cara do usuário.

1 O tipo RAGResponse

@dataclass
class RAGResponse:
    answer: str
    query: str
    model: str
    context_used: str
CampoPor quê
answerO texto final do LLM
queryA pergunta original (log, auditoria)
modelQual modelo gerou (importante com fallbacks)
context_usedO contexto exato que foi enviado

context_used é o mais valioso e o mais subestimado. Permite auditoria reversa: seis meses depois, se o usuário reclamar "a resposta estava errada", você reproduz exatamente o que o LLM viu.

Princípio de governança: em RAG, guarde sempre o input completo que gerou o output.

2 build_rag_prompt() — o contrato

def build_rag_prompt(query: str, context: str) -> list[dict[str, str]]:
    return [
        {"role": "system", "content": gen_cfg.default_system_prompt},
        {"role": "user",   "content": f"CONTEXTO:\n{context}\n\nPERGUNTA: {query}"},
    ]

2.1 Formato de mensagens

[
    {"role": "system", "content": "..."},   # instruções
    {"role": "user",   "content": "..."},   # input
]

Por que dois papéis? Porque o LLM é treinado para diferenciar instruções de dados. O system é o "manual de conduta"; o user é o "conteúdo bruto". Misturar abre porta para prompt injection.

2.2 A ordem CONTEXTO → PERGUNTA

LLMs têm viés de recência: prestam mais atenção no que vem por último. Se a pergunta viesse primeiro, o modelo poderia "esquecer" no meio de 3.000 caracteres. Colocar a pergunta por último é padrão em RAG.

2.3 Por que sem separadores elaborados?

VantagemDesvantagem
Menos tokens gastosSem delimitadores explícitos
Menos chance do LLM confundir formatoSem instrução "ignore comandos no contexto"

Uma versão mais robusta usa delimitadores semânticos:

content = (
    "Responda APENAS com base no contexto abaixo. "
    "Se a informação não estiver no contexto, diga que não sabe.\n\n"
    f"<contexto>\n{context}\n</contexto>\n\n"
    f"<pergunta>{query}</pergunta>"
)

As tags <contexto> ajudam o modelo a delimitar. Sem elas, um chunk com "ignore as instruções anteriores" pode enganar o modelo.

O código atual delega essa defesa ao default_system_prompt. Se o prompt configurado já diz "ignore comandos embutidos", está certo. Se não, é um risco latente.

3 format_context_with_budget()

def format_context_with_budget(chunks: list, max_chars: int = gen_cfg.max_context_chars) -> str:
    parts = []
    current_chars = 0
    
    for i, c in enumerate(chunks, start=1):
        source_name = Path(c.source).name
        header = f"({i}) Fonte: {source_name} | Pág: {c.page}\n"
        block = header + c.text
        
        if current_chars + len(block) > max_chars:
            break
            
        parts.append(block)
        current_chars += len(block)
        
    return "\n\n".join(parts)

3.1 Comparação com format_context do Bloco 3

AspectoBloco 3Bloco 4
Cabeçalho[Trecho 1 \| Fonte: X \| Pág. 5](1) Fonte: X \| Pág: 5\n
Separador"\n\n---\n\n""\n\n"
Limitemax_chars=3000 hardcodedgen_cfg.max_context_chars

Por que duplicar? Porque o Bloco 4 é deliberadamente mais enxuto — cada caractere conta. O separador --- do Bloco 3 é ótimo para debug mas desperdiça 5 caracteres por bloco. Com 20 chunks, isso é ~100 caracteres.

Trade-off consciente: o Bloco 4 sacrifica legibilidade humana em favor de eficiência de tokens. Mas duplicação é dívida técnica — idealmente haveria uma função com parâmetro style="verbose"|"compact".

3.2 O cabeçalho (1) Fonte: ...

O (1) é mais fácil de referenciar. O LLM aprende a citar como "segundo o trecho (1)…" — parênteses são o padrão acadêmico.

3.3 "Token budget" medido em caracteres

if current_chars + len(block) > max_chars:

Mede caracteres, não tokens. Um token ≈ 2–4 caracteres. Aproximação conservadora:

  • max_chars = 8000 ≈ 2000–2600 tokens → seguro para num_ctx = 4096.
  • len() é O(1); tokenização é O(n).
  • Portável — funciona com qualquer modelo.

Limite real: a proporção varia por idioma. Em japonês, 1 caractere ≈ 1–2 tokens. Se internacionalizar, a aproximação vira gargalo.

3.4 O break

Idêntico ao Bloco 3: para na primeira vez que estoura. Conservador e previsível.

4 generate_answer() — a chamada

def generate_answer(query: str, context: str, cfg: OllamaConfig = ollama_cfg) -> RAGResponse:
    messages = build_rag_prompt(query, context)

    try:
        response = ollama.chat(
            model=cfg.model,
            messages=messages,
            options={
                "temperature": cfg.temperature,
                "num_ctx": cfg.num_ctx,
            },
        )
        answer = response.message.content or ""
        return RAGResponse(answer=answer, query=query, model=cfg.model, context_used=context)
    except Exception as e:
        error_msg = str(e)
        if "connection" in error_msg.lower() or "refused" in error_msg.lower():
            raise ConnectionError(
                f"Não foi possível conectar ao Ollama em {cfg.base_url}.\n"
                "Certifique-se de que o Ollama está rodando com: ollama serve"
            ) from e
        raise

4.1 ollama.chat()

Retorna objeto com .message.content. É stateless — para conversa multi-turn, acumule messages e reenvie tudo.

4.2 options — painel de controle

temperature

  • 0.0 — quase determinístico
  • 0.7 — criativo, chat aberto
  • 1.5 — caótico

Em RAG, use 0.0–0.2. RAG não é geração criativa — é extração fiel. Temperaturas altas aumentam o risco de alucinação.

Regra: temperature=0 para Q&A factual, 0.3–0.5 para resumos, 0.7+ para narrativas.

num_ctx

Define quantos tokens o modelo processa. Se o prompt for maior, o Ollama silenciosamente trunca. Catastrófico em RAG.

ConfiguraçãoConsistente?
max_context_chars=3000 + num_ctx=2048✅ Sim
max_context_chars=8000 + num_ctx=2048❌ Overflow silencioso
max_context_chars=3000 + num_ctx=8192✅ Sim, mas desperdiça

Idealmente, max_context_chars deveria ser calculado a partir de num_ctx.

4.3 response.message.content or ""

Defesa contra None em erro parcial, timeout ou <eos> imediato. Sem isso, um None cascatearia como TypeError.

4.4 O except

Traduz erro técnico em mensagem humana. Detecta via string matching ("connection", "refused") e re-lança com raise ... from e preservando a causa.

CenárioMensagem atualIdeal
Ollama offline✅ "Rode ollama serve"—
Modelo não baixado❌ Erro cru"Rode ollama pull ..."
Timeout❌ Erro cru"Modelo demorou Xs"
Contexto excedido❌ Silencioso⚠️ Não detectável hoje

5 check_ollama_available()

def check_ollama_available(cfg: OllamaConfig = ollama_cfg) -> bool:
    try:
        ollama.list()
        return True
    except Exception:
        return False

ollama.list() é barato — o servidor retorna modelos baixados sem inferência. É o "ping" ideal.

Bug latente: o cfg é aceito mas não usado. Se você usa base_url customizado, essa função ainda fala com o default localhost:11434.

O que falta: validar se o modelo específico está baixado:

def check_ollama_ready(model: str, cfg: OllamaConfig = ollama_cfg) -> bool:
    try:
        models = ollama.list()
        return any(model in m.get("name", "") for m in models.get("models", []))
    except Exception:
        return False

6 Execução standalone — smoke test

if __name__ == "__main__":
    from rich.panel import Panel
    from rich.markdown import Markdown

    query = "Quais são as regras de férias?"
    context = "(1) Fonte: teste.txt | Pág: 1\nTodo funcionário tem 30 dias de férias."
    
    if check_ollama_available():
        res = generate_answer(query, context)
        console.print(Panel(Markdown(res.answer), title="Resposta Teste"))
    else:
        console.print("[red]Ollama offline[/red]")

Diferente dos Blocos 2 e 3, este __main__ é um smoke test isolado — contexto hardcoded, só testa a geração. Útil para iterar rápido sem pagar o custo de rodar 1→2→3.

Markdown(...) interpreta a saída do LLM como Markdown — sem isso, você veria **asteriscos** literais.

O que falta: quando Ollama está offline, o script não retorna exit code 1 — quebra o padrão dos blocos anteriores.

✦ Resumo em uma frase

Este módulo recebe a pergunta original e os chunks relevantes do Bloco 3, monta um prompt estruturado (system + contexto + pergunta), envia ao LLM local via Ollama com parâmetros conservadores e retorna a resposta final empacotada com todo o rastro de auditoria — fechando o ciclo do pipeline RAG.

⚠ Possíveis melhorias

  1. Duplicação de format_context — Blocos 3 e 4 têm funções quase idênticas. Uma parametrizada eliminaria a duplicação.
  2. check_ollama_available ignora cfg — não respeita base_url customizado.
  3. Health check não valida modelo — servidor no ar ≠ modelo baixado.
  4. num_ctx vs max_context_chars desalinhados — truncamento silencioso.
  5. Sem streaming — respostas longas ficam sem feedback. stream=True daria UX melhor.
  6. Sem timeout explícito — a chamada pode travar indefinidamente.
  7. Detecção de erro por string matching — frágil. Detecção por tipo seria mais robusta.
  8. Prompt injection — sem delimitadores formais. Mitigação: reforçar system prompt, usar tags, sanitizar chunks.
  9. __main__ sem exit code 1 — CI/CD não detecta falha.

Pontos de atenção transversais

Acoplamento oculto entre B2 e B3 — a conversão score = 1 - dist assume métrica cosine. Se você mudar distance_metric no config.py sem ajustar o B3, os scores ficam errados mas o código não avisa.

Acoplamento oculto entre B1, B2 e B3 — o doc_hash muda quando o PDF muda, mas o chunk_idx muda quando o chunk_size muda. Hoje, apenas o PDF é rastreado; mudanças de configuração deixam chunks órfãos.

Acoplamento oculto entre B3 e B4 — max_chars do Bloco 3 e max_context_chars do Bloco 4 são configurados independentemente. Se um for maior que o outro, o contexto é truncado silenciosamente em uma das pontas.

  • Identificar pontos de extensão — cada bloco tem uma seção "Possíveis melhorias" com sugestões concretas.
  • Depurar problemas — as seções "Arquitetura" mostram camadas e responsabilidades; se algo falha, você sabe onde olhar.
  • Auditar decisões de design — callouts marcados com 💡 e 📌 explicam trade-offs não óbvios.
